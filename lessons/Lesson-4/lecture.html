1. Что такое переменная

1. What a variable is

Переменная — это именованный «контейнер» для хранения данных. Вы даёте контейнеру имя, кладёте туда значение, а потом обращаетесь к нему по имени.

A variable is a named "container" for holding data. You give the container a name, put a value inside, then refer to it by name.

let age = 18;          // создали контейнер "age", положили в него число 18
console.log(age);      // обратились к контейнеру по имени → выведет 18
age = 19;              // заменили значение в контейнере на 19
console.log(age);      // → 19

Аналогия: переменная — это ящик в гардеробе. На ящике написано имя («age»), внутри лежит ваша вещь (18). Когда вам нужна эта вещь — вы говорите её имя, и вам её достают. Можно положить новую вещь — старая выкинется.

Analogy: a variable is a locker in a coatroom. The locker has a name ("age") and your stuff inside (18). When you need it, you say the name and they fetch it. You can put a new item in — the old one is thrown out.

В JavaScript (а значит и в TypeScript) переменные объявляются тремя ключевыми словами: let, const и var. Они выглядят похоже, но ведут себя по-разному.

In JavaScript (and therefore TypeScript) variables are declared with three keywords: let, const, and var. They look similar but behave differently.

2. let, const и почему не var

2. let, const, and why not var

let — переменная, значение которой можно менять

let — a variable whose value can change

let score = 0;
score = 10;       // ✅ можно
score = 100;      // ✅ снова можно
console.log(score);  // → 100

const — константа, значение нельзя переназначить

const — a constant, value cannot be reassigned

const pi = 3.14;
pi = 3.15;        // ❌ Cannot assign to 'pi' because it is a constant.

Важная тонкость: const запрещает переназначение, но не изменение содержимого. Для объектов и массивов это значит: ссылку поменять нельзя, а вот сам объект — можно.

Subtle point: const forbids reassignment, not mutation. For objects and arrays this means: you can't swap the reference, but the object itself can still change.

const user = { name: "Anna" };
user = { name: "Boris" };   // ❌ нельзя — это переназначение
user.name = "Boris";        // ✅ можно — это изменение поля внутри объекта

const list = [1, 2, 3];
list = [4, 5, 6];           // ❌ нельзя
list.push(4);               // ✅ можно — добавили элемент в существующий массив

var — устаревший способ, в 2026 году не используется

var — the legacy way, not used in 2026

До 2015 года var был единственным способом объявить переменную в JavaScript. У него были серьёзные проблемы:

Before 2015, var was the only way to declare a variable in JavaScript. It had serious problems:

  • Function scope: var видна во всей функции, даже если объявлена внутри if или for
  • Hoisting: переменную можно использовать до её объявления (часто ведёт к багам)
  • Можно повторно объявить: var x = 1; var x = 2; — никакой ошибки
  • Function scope: var is visible across the whole function, even if declared inside if or for
  • Hoisting: the variable can be used before its declaration (a common source of bugs)
  • Re-declaration allowed: var x = 1; var x = 2; — no error

Правило 2026: в новом коде никогда не используйте var. По умолчанию пишите const; если значение реально нужно менять — let. Если в коллеге увидели var — это знак, что код древний или его автор не следил за стандартами.

2026 rule: in new code never use var. Default to const; if the value really needs to change — use let. If you see var in a colleague's code, it's a sign the code is ancient or the author isn't following modern standards.

3. Аннотация типа — синтаксис

3. Type annotation — syntax

До сих пор мы писали как в JavaScript. Теперь — главное отличие TypeScript: аннотация типа. Вы пишете после имени переменной двоеточие и тип, который ожидаете.

Up to here we wrote pure JavaScript. Now — the main TypeScript difference: type annotation. You write a colon and the expected type after the variable name.

let age: number = 18;            // тип number
let userName: string = "Anna";   // тип string
let isAdmin: boolean = false;    // тип boolean

Формула: let <имя>: <тип> = <значение>;

Formula: let <name>: <type> = <value>;

Теперь TypeScript гарантирует, что в эту переменную никогда не попадёт значение другого типа:

Now TypeScript guarantees that a value of another type can never get into this variable:

let age: number = 18;
age = 19;              // ✅
age = "девятнадцать";  // ❌ Type 'string' is not assignable to type 'number'.

Эта ошибка появится прямо в редакторе, ещё до запуска кода. Это и есть главная суперспособность TypeScript — ловить такие баги до того, как они доберутся до пользователя.

This error shows up right in the editor, before the code even runs. That's TypeScript's main superpower — catching such bugs before they reach a user.

4. Type inference — TypeScript «угадывает» тип

4. Type inference — TypeScript "guesses" the type

А теперь — главный сюрприз для новичков: в большинстве случаев аннотацию типа писать не нужно. TypeScript умеет сам определить тип по значению, которое вы присваиваете. Это называется type inference («вывод типа»).

And now — a surprise for beginners: in most cases you don't need to write a type annotation. TypeScript can determine the type itself from the value you assign. This is called type inference.

let age = 18;            // TS сам понял: age — это number
let userName = "Anna";   // TS сам понял: userName — это string
let isAdmin = false;     // TS сам понял: isAdmin — это boolean

age = "нет";             // ❌ Type 'string' is not assignable to type 'number'.
userName = 42;           // ❌ Type 'number' is not assignable to type 'string'.

Это удивляет всех, кто только пришёл в TypeScript: вы не писали : number, но защита от ошибок типов работает. Это и есть type inference в действии. TypeScript «смотрит» на значение 18, понимает «это число», и навсегда фиксирует за переменной тип number.

This surprises every TypeScript newcomer: you didn't write : number, but type safety still works. That's type inference in action. TypeScript "looks" at the value 18, decides "that's a number", and pins the type number to the variable forever.

Проверьте сами в VS Code: наведите курсор на age. Появится подсказка: let age: number. Это TypeScript показывает, какой тип он вывел.

See for yourself in VS Code: hover the cursor over age. A tooltip appears: let age: number. That's TypeScript showing the type it inferred.

Где inference работает

Where inference works

  1. При объявлении переменной с инициализацией: let x = 5
  2. При возврате значения из функции: TS выводит тип возврата автоматически
  3. При обращении к свойству объекта: const u = { name: "Anna" }; u.name → string
  4. В большинстве выражений: const sum = 2 + 3 → number
  1. When declaring a variable with initializer: let x = 5
  2. When returning from a function: TS infers the return type automatically
  3. When accessing an object's property: const u = { name: "Anna" }; u.name → string
  4. In most expressions: const sum = 2 + 3 → number

Где inference НЕ работает (нужна аннотация)

Where inference does NOT work (annotation required)

  1. Объявление без значения: let x; → TS думает: any (плохо). Нужно let x: number;
  2. Параметры функции: function f(x) { ... } — TS не знает тип x, надо писать function f(x: number)
  3. Когда у значения несколько возможных типов: let id = Math.random() > 0.5 ? 1 : "one"; → можно явно указать let id: number | string = ...
  1. Declaration without a value: let x; → TS assumes any (bad). You need let x: number;
  2. Function parameters: function f(x) { ... } — TS doesn't know x's type, write function f(x: number)
  3. When the value has several possible types: let id = Math.random() > 0.5 ? 1 : "one"; → you can spell it out let id: number | string = ...

5. Widening: let vs const с литералами

5. Widening: let vs const with literals

Тонкий, но очень важный момент. Inference ведёт себя по-разному для let и const:

A subtle but very important point. Inference behaves differently for let and const:

let x = "hello";    // тип: string  ← «расширенный» (widened) тип
const y = "hello";  // тип: "hello"  ← литеральный (literal) тип

Почему так: let можно переназначить, поэтому TS «расширяет» (widening) тип до общего — string вместо точного "hello". А const переназначить нельзя — значит, в переменной навсегда будет именно "hello", и TS использует литеральный тип.

Why: let can be reassigned, so TS "widens" the type to a more general one — string instead of the exact "hello". const can't be reassigned — so the variable will forever hold exactly "hello", and TS uses the literal type.

Зачем это знать? Литеральные типы — это сила. Они позволяют создавать переменные с точным значением, что критично для union-типов в будущих занятиях:

Why does this matter? Literal types are powerful. They let you create variables with an exact value, which is crucial for union types in upcoming lessons:

const direction = "left";   // тип: "left" (литеральный)

// В будущем:
type Direction = "left" | "right" | "up" | "down";
const move: Direction = "left";  // ✅
const move: Direction = "diagonal";  // ❌ — нет в списке

Запомните:

  • let x = 5 → number
  • const x = 5 → 5
  • let s = "hi" → string
  • const s = "hi" → "hi"

Remember:

  • let x = 5 → number
  • const x = 5 → 5
  • let s = "hi" → string
  • const s = "hi" → "hi"

6. Главное правило 2026: «аннотируй границы»

6. The 2026 headline rule: "annotate boundaries"

Вы только что узнали, что TypeScript часто сам угадывает тип. Возникает вопрос: а когда вообще писать : number, если можно не писать?

You just learned that TypeScript often guesses types on its own. So when do you ever write : number, if you can skip it?

Правило 2026 года: «Аннотируй границы — параметры функций и явный возврат. Доверяй inference внутри.»

2026 rule: "Annotate the boundaries — function parameters and explicit returns. Trust inference inside."

Что значит «границы»

What "boundaries" means

Границы — это места, где код принимает или отдаёт данные: параметры функций, тип возвращаемого значения, экспорт из модуля. В этих местах аннотации обязательны — иначе TS не сможет проверять, что внешний код передаёт правильные данные.

Boundaries are places where code receives or returns data: function parameters, return type, module exports. Annotations there are mandatory — otherwise TS can't verify that external code passes the right data.

// ✅ Границы: параметры и возврат — аннотированы
function calculatePrice(price: number, quantity: number): number {
    // ✅ Внутри: доверяем inference
    const total = price * quantity;  // total: number (выведено)
    const message = `Итого: ${total}`;  // message: string (выведено)
    return total;
}

Антипример: «всё подряд аннотируем»

Anti-example: "annotate everything"

// ❌ Слишком много аннотаций — шум, ничего не добавляет
function calculatePrice(price: number, quantity: number): number {
    const total: number = price * quantity;
    const message: string = `Итого: ${total}`;
    const taxRate: number = 0.13;
    const taxed: number = total * (1 + taxRate);
    return taxed;
}

Все эти внутренние : number и : string — лишние. TS и так бы их вывел. Хорошие разработчики пишут код лаконичнее:

All those inner : number and : string are unnecessary. TS would infer them anyway. Good developers write more concisely:

// ✅ Идиоматический TypeScript 2026
function calculatePrice(price: number, quantity: number): number {
    const total = price * quantity;
    const taxRate = 0.13;
    const taxed = total * (1 + taxRate);
    return taxed;
}

Профессионалы говорят: «TypeScript — это не больше кода, а меньше багов». Если вы пишете в два раза больше TS, чем JS, — что-то не так с подходом. Хорошо настроенный TS добавляет 5-10% объёма за счёт аннотаций границ — и убирает 90% багов.

Pros say: "TypeScript isn't more code, it's fewer bugs". If your TS is twice the size of equivalent JS — your approach is off. Well-tuned TS adds 5-10% volume via boundary annotations — and removes 90% of bugs.

8. Чтение TS-ошибок: «is not assignable to»

8. Reading TS errors: "is not assignable to"

Самая частая ошибка в TypeScript — Type 'X' is not assignable to type 'Y'. Разберём, как её читать.

The most common TypeScript error is Type 'X' is not assignable to type 'Y'. Let's learn how to read it.

let age: number = 18;
age = "девятнадцать";
//    ~~~~~~~~~~~~~~~
// Type 'string' is not assignable to type 'number'.

Расшифровка слово за словом:

Word-by-word breakdown:

  • Type 'string' — тип того, что вы пытаетесь положить
  • is not assignable to — «нельзя присвоить»
  • type 'number' — тип переменной, в которую кладёте
  • Type 'string' — the type of the value you're trying to put in
  • is not assignable to — "cannot be assigned to"
  • type 'number' — the type of the variable you're putting it into

Перевод на человеческий: «вы пытаетесь положить строку в переменную, которая ожидает число».

Translation to human: "you're trying to put a string into a variable that expects a number".

Как чинить:

  1. Если вы передаёте не то значение — поправьте значение.
  2. Если у переменной неправильный тип — поправьте тип.
  3. Если действительно надо разные типы — используйте union (об этом в занятии 18).

How to fix:

  1. If you're passing the wrong value — fix the value.
  2. If the variable has the wrong type — fix the type.
  3. If you really need multiple types — use a union (we'll see that in Lesson 18).

9. Hoisting и Temporal Dead Zone

9. Hoisting and the Temporal Dead Zone

Короткий, но важный раздел. JavaScript «поднимает» (hoists) объявления переменных в начало скоупа. Поведение разное для var и let/const.

A short but important section. JavaScript "hoists" variable declarations to the top of the scope. The behavior differs for var and let/const.

// var: можно использовать ДО объявления — значение undefined
console.log(x);   // → undefined (не ошибка!)
var x = 5;

// let/const: ошибка при использовании до объявления (TDZ)
console.log(y);   // ❌ ReferenceError: Cannot access 'y' before initialization
let y = 5;

TDZ (Temporal Dead Zone) — это «мёртвая зона» с начала скоупа до строки объявления let/const. В этой зоне переменная существует, но обращаться к ней нельзя. Это защитный механизм — он не даёт случайно использовать переменную «до создания».

TDZ (Temporal Dead Zone) is the "dead zone" between the start of the scope and the let/const declaration line. In this zone the variable exists but can't be accessed. This is a safety mechanism — it stops you from accidentally using a variable "before it's born".

Это ещё одна причина не использовать var: с ним легко случайно прочитать переменную до её объявления и получить тихий undefined вместо понятной ошибки.

Yet another reason to avoid var: it makes it easy to accidentally read a variable before its declaration and get a silent undefined instead of a clear error.

10. Правила именования переменных

10. Variable naming rules

Имя переменной — это первое, что увидит читатель кода (включая «будущего вас» через 3 месяца). Хорошее имя экономит часы понимания.

A variable name is the first thing a code reader sees (including "future you" three months from now). A good name saves hours of reading.

Технические правила (заставит TS)

Technical rules (enforced by TS)

  • Имя начинается с буквы, _ или $
  • Дальше — буквы, цифры, _, $ (без пробелов и дефисов)
  • Нельзя совпадать с ключевыми словами (let, const, function, class...)
  • Чувствительно к регистру: age и Age — разные переменные
  • Name starts with a letter, _, or $
  • Then — letters, digits, _, $ (no spaces or hyphens)
  • Can't match keywords (let, const, function, class...)
  • Case-sensitive: age and Age are different variables

Хорошие vs плохие имена

Good vs bad names

❌ Плохо
❌ Bad

let userAge = 25;

Правило: «код читается в 10 раз чаще, чем пишется». Сэкономили секунду на наборе d вместо createdAt — потратили 10 минут на понимание через неделю.

Rule: "code is read 10x more often than it's written". You saved a second typing d instead of createdAt — and spent 10 minutes a week later figuring out what it means.

  • Переменная — именованный контейнер для значения.
  • const по умолчанию, let если нужно менять, var — никогда.
  • const запрещает переназначение, но не изменение полей объекта/массива.
  • Аннотация типа: let x: number = 5. Гарантирует, что TS будет проверять тип.
  • Type inference — TS сам определяет тип по значению. Работает почти везде.
  • Widening: let x = "hi" → string, но const x = "hi" → "hi" (литерал).
  • Правило 2026: аннотируй границы (параметры, возврат), доверяй inference внутри.
  • Аннотируй обязательно: параметры функций, объявления без значения, данные с границы системы.
  • Не аннотируй: внутренние переменные функций, очевидные литералы.
  • Ошибка Type 'X' is not assignable to type 'Y' = «вы передаёте X туда, где ждут Y».
  • TDZ защищает от использования let/const до их объявления.
  • camelCase для переменных, PascalCase для типов, UPPER_SNAKE_CASE для констант.
  • A variable is a named container for a value.
  • const by default, let if it needs to change, var — never.
  • const forbids reassignment but not mutation of object/array fields.
  • Type annotation: let x: number = 5. Forces TS to check the type.
  • Type inference — TS figures out the type from the value. Works almost everywhere.
  • Widening: let x = "hi" → string, but const x = "hi" → "hi" (literal).
  • 2026 rule: annotate boundaries (parameters, returns), trust inference inside.
  • Must annotate: function parameters, declarations with no value, data from the system boundary.
  • Don't annotate: local variables inside functions, obvious literals.
  • The error Type 'X' is not assignable to type 'Y' = "you're passing X where Y is expected".
  • TDZ prevents using let/const before declaration.
  • camelCase for variables, PascalCase for types, UPPER_SNAKE_CASE for constants.
