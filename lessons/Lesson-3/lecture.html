1. Что такое tsconfig.json и зачем он нужен

1. What tsconfig.json is and why we need it

В занятии 2 мы запускали npx tsc hello.ts — передавали имя файла прямо в командной строке. Это работает для одного файла, но не для настоящего проекта. В реальном проекте — десятки и сотни .ts-файлов, и каждый запуск с длинной командой превращается в кошмар.

In Lesson 2 we ran npx tsc hello.ts — passing the file name on the command line. That works for one file, but not for a real project. A real project has dozens or hundreds of .ts files, and running each one with a long command is a nightmare.

tsconfig.json — это конфигурационный файл TypeScript-проекта. Лежит в корне проекта. Описывает: какие файлы компилировать, в какую версию JavaScript, насколько строго проверять типы, куда складывать результат и десятки других опций. Если этот файл присутствует, достаточно команды npx tsc без аргументов — компилятор сам прочитает конфиг и сделает всё правильно.

tsconfig.json is the configuration file of a TypeScript project. It lives at the project root. It describes: which files to compile, which JavaScript version to target, how strictly to check types, where to put the output, and dozens of other options. When this file is present, the bare command npx tsc is enough — the compiler reads the config and does everything correctly.

Аналогия: package.json — это «паспорт проекта» для npm (имя, зависимости, скрипты). tsconfig.json — это «инструкция для компилятора TypeScript»: как именно превращать ваш TS в JS и что считать ошибкой.

Analogy: package.json is the project's "passport" for npm (name, dependencies, scripts). tsconfig.json is the "instruction manual for the TypeScript compiler" — how exactly to turn your TS into JS and what to count as an error.

Главное: поведение TypeScript на 80% определяется файлом tsconfig.json. Один и тот же код в одном проекте — валидный, в другом — гора ошибок. Разница только в конфиге. Поэтому правильная настройка tsconfig.json — это не «деталь», а половина успеха.

The key insight: TypeScript's behavior is 80% determined by tsconfig.json. The same code is valid in one project and a pile of errors in another — the only difference is the config. So getting tsconfig.json right isn't a "detail", it's half the battle.

3. Генерируем tsconfig: npx tsc --init

3. Generating tsconfig: npx tsc --init

Писать tsconfig.json с нуля не нужно. У компилятора есть встроенная команда, которая создаёт файл с сотней опций — большинство закомментированы, рядом подробные пояснения.

You don't need to write tsconfig.json from scratch. The compiler has a built-in command that creates a file with about a hundred options — most commented out, each with a clear inline explanation.

npx tsc --init

В корне проекта появится tsconfig.json размером ~5 КБ. Это стартовый шаблон. Откройте его и пролистайте — увидите, что он состоит из одной большой секции "compilerOptions" с включёнными и закомментированными опциями.

A tsconfig.json of about 5 KB appears at the project root. This is a starter template. Open it and scroll — you'll see one big "compilerOptions" section with enabled and commented-out options.

Внутри он выглядит примерно так (с урезанными комментариями):

It looks roughly like this (comments trimmed):

{
  "compilerOptions": {
    "target": "es2016",                  // версия JS на выходе
    "module": "commonjs",                // формат модулей
    "esModuleInterop": true,             // совместимость с CommonJS-модулями
    "forceConsistentCasingInFileNames": true,
    "strict": true,                      // главный флаг строгости
    "skipLibCheck": true                 // не проверять типы внутри node_modules
  }
}

Внимание: сгенерированный шаблон ориентирован на «среднестатистический» проект 2018-2020 годов. Для современного TypeScript 2026 года мы заменим несколько ключевых опций — иначе будем писать «вчерашний» код.

Heads up: the generated template is aimed at the "average" project of 2018-2020. For modern 2026 TypeScript we'll replace several key options — otherwise we'll be writing "yesterday's" code.

4. Анатомия tsconfig.json: 6 ключевых опций

4. Anatomy of tsconfig.json: 6 key options

Из сотни опций tsconfig.json 95% времени вам понадобятся шесть. Разберём каждую.

Of tsconfig.json's hundred options, 95% of the time you'll need just six. Let's go through each.

4.1. target — в какую версию JavaScript компилировать

4.1. target — which JavaScript version to compile to

TypeScript умеет компилировать ваш код в разные версии JavaScript: от древней ES5 (для старых браузеров) до самой свежей ESNext. Чем новее target, тем больше синтаксиса остаётся «как написано» — без переписывания в более старую форму.

TypeScript can compile your code to different JavaScript versions: from ancient ES5 (for old browsers) to bleeding-edge ESNext. The newer the target, the more syntax stays "as written" — without being rewritten into older forms.

4.2. module — формат модулей

4.2. module — module format

Опция говорит, какой синтаксис модулей будет в выходном .js: устаревший CommonJS (require/module.exports) или современный ES Modules (import/export).

This option tells which module syntax goes into the output .js: legacy CommonJS (require/module.exports) or modern ES Modules (import/export).

4.3. moduleResolution — как искать импортируемые модули

4.3. moduleResolution — how to find imported modules

Когда вы пишете import { x } from "./utils", компилятор должен найти, в каком файле этот x лежит. Алгоритм поиска зависит от рантайма.

When you write import { x } from "./utils", the compiler must find which file contains this x. The lookup algorithm depends on the runtime.

  • "node10" (он же "node") — старый стиль, для CommonJS-проектов
  • "nodenext" ✓ — современный Node.js 22+ (требует module: "nodenext")
  • "bundler" ✓ — для проектов со сборщиком (Vite, webpack). Самый удобный для фронта.
  • "node10" (a.k.a. "node") — old style, for CommonJS projects
  • "nodenext" ✓ — modern Node.js 22+ (requires module: "nodenext")
  • "bundler" ✓ — for projects with a bundler (Vite, webpack). Most convenient for frontend.

4.4. rootDir и outDir — где исходники и куда класть результат

4.4. rootDir and outDir — where sources are and where output goes

"rootDir": "./src",       // папка с .ts-файлами
"outDir":  "./dist"       // папка для скомпилированных .js

Без этих опций компилятор положит .js рядом с .ts — и проект превратится в свалку. С этими опциями структура остаётся чистой:

Without these, the compiler drops .js next to .ts — and your project becomes a mess. With them, the structure stays clean:

ts-strict-demo/ ├── src/ │ ├── index.ts │ └── utils.ts ├── dist/ ← создаётся компилятором │ ├── index.js │ └── utils.js ├── package.json └── tsconfig.json

4.5. include и exclude — какие файлы компилировать

4.5. include and exclude — which files to compile

"include": ["src/**/*"],          // все .ts-файлы внутри src/
"exclude": ["node_modules", "dist"]  // эти папки игнорируем

Без include компилятор пытается обработать все .ts-файлы в проекте — включая случайные временные. Явное указание include избавляет от сюрпризов.

Without include, the compiler tries to process every .ts file in the project — including stray temp files. An explicit include prevents surprises.

4.6. strict — главный флаг (про него следующий раздел)

4.6. strict — the headline flag (next section is about it)

5. Strict-режим: главный флаг 2026 года

5. Strict mode: the headline 2026 flag

"strict": true — самая важная строчка в tsconfig.json. Она включает разом восемь отдельных опций строгости. Без неё TypeScript ведёт себя «снисходительно» и пропускает половину ошибок. Со strict: true вы получаете настоящий TypeScript, ради которого этот язык и существует.

"strict": true is the single most important line in tsconfig.json. It enables eight strictness options at once. Without it, TypeScript behaves "leniently" and lets half the errors slip through. With strict: true you get real TypeScript — what the language was built for.

Анти-паттерн: «отключим strict, у нас слишком много ошибок». Это всё равно что снять детектор дыма, потому что он часто пищит. Ошибки никуда не делись — они теперь просто невидимы и взорвутся в проде.

Anti-pattern: "let's turn off strict, we have too many errors". That's like removing the smoke detector because it beeps too often. The errors didn't go away — they're just invisible now and will explode in production.

6. 5 ключевых флагов 2026 года

6. 5 essential 2026 flags

Кроме strict: true, в 2026 году принято включать ещё несколько отдельных флагов. Они не входят в strict, но за последние годы стали стандартом качественных проектов.

Beyond strict: true, the 2026 norm is to enable a few more separate flags. They're not part of strict, but in recent years they've become the standard for quality projects.

6.1. noUncheckedIndexedAccess

6.1. noUncheckedIndexedAccess

Без флага: arr[0] возвращает T. Но это ложь — массив может быть пустым, и arr[0] на самом деле undefined. Со флагом: arr[0] возвращает T | undefined — и TypeScript заставит проверить.

Without the flag: arr[0] returns T. But that's a lie — the array might be empty, and arr[0] is actually undefined. With the flag: arr[0] returns T | undefined — and TypeScript forces you to check.

const users: string[] = ["Anna", "Boris"];

// Без флага: TS думает, что user — это string
const user = users[100];   // на самом деле undefined!
console.log(user.toUpperCase());  // 💥 крашится в рантайме

// Со флагом noUncheckedIndexedAccess: тип user — string | undefined
const user = users[100];
console.log(user.toUpperCase());  // ❌ TS: 'user' is possibly 'undefined'
// → нужно проверить: if (user) { user.toUpperCase() }

6.2. verbatimModuleSyntax

6.2. verbatimModuleSyntax

Заставляет писать import type явно, когда импортируется только тип. Это критично для современных раннеров (tsx, Bun, Node native) — они не умеют «угадывать», что именно тип, а что — значение.

Forces you to write import type explicitly when only a type is imported. Critical for modern runners (tsx, Bun, Node native) — they can't "guess" what's a type and what's a value.

// Без флага — работает, но непонятно, тип это или нет:
import { User } from "./types";

// С флагом — явно и однозначно:
import type { User } from "./types";   // только тип
import { createUser } from "./api";    // только значение

6.3. noImplicitOverride

6.3. noImplicitOverride

При переопределении метода в дочернем классе нужно явно писать override. Без этого можно «случайно» переопределить метод и сломать родительский класс — TS не подскажет.

Overriding a method in a subclass requires an explicit override keyword. Without it you can "accidentally" override a method and break the parent class — TS won't warn you.

class Animal {
  speak() { return "..."; }
}

class Dog extends Animal {
  override speak() { return "Woof!"; }   // явно: я переопределяю
}

6.4. exactOptionalPropertyTypes

6.4. exactOptionalPropertyTypes

Различает «поля нет» и «поле есть и оно undefined». Без флага оба варианта одинаковы — это путает.

Distinguishes "field absent" from "field present and equal to undefined". Without the flag, both look the same — which is confusing.

type User = { name: string; nickname?: string };

// Без флага оба ОК:
const a: User = { name: "Anna" };                  // ОК
const b: User = { name: "Anna", nickname: undefined };  // тоже ОК

// Со флагом — второй вариант запрещён, надо именно НЕ указывать поле

6.5. skipLibCheck (исключение — этот включают для скорости)

6.5. skipLibCheck (the exception — this one's enabled for speed)

Включён по умолчанию в шаблоне. Не проверяет типы внутри node_modules. Оставляем включённым — ускоряет компиляцию в десятки раз и не теряет полезных ошибок (свой код всё равно проверяется).

Enabled by default in the template. Skips type-checking inside node_modules. Keep it on — speeds up compilation tenfold and loses no useful errors (your own code is still fully checked).

7. Финальный tsconfig.json для курса

7. Final tsconfig.json for the course

Соберём всё вместе. Замените содержимое сгенерированного tsconfig.json на это:

Putting it all together. Replace the generated tsconfig.json with this:

{
  "compilerOptions": {
    // Версия итогового JavaScript
    "target": "ES2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",

    // Структура папок
    "rootDir": "./src",
    "outDir": "./dist",

    // Главные флаги строгости (включают много опций сразу)
    "strict": true,

    // 4 дополнительных флага качества 2026 года
    "noUncheckedIndexedAccess": true,
    "verbatimModuleSyntax": true,
    "noImplicitOverride": true,
    "exactOptionalPropertyTypes": true,

    // Удобства
    "sourceMap": true,        // отладка по .ts-файлу
    "declaration": true,      // создавать .d.ts файлы
    "esModuleInterop": true,  // импорт CommonJS-модулей как ESM
    "skipLibCheck": true,     // не проверять node_modules (быстрее)
    "forceConsistentCasingInFileNames": true
  },
  "include": ["src/**/*"],
  "exclude": ["node_modules", "dist"]
}

Этот конфиг — основа всего курса. Запомните его или сохраните как шаблон.

This config is the foundation of the whole course. Memorize it or save as a template.

Чтобы Node.js понял ESM-модули, в package.json добавьте одну строку: "type": "module". Без неё Node будет считать .js-файлы CommonJS-модулями, и импорты сломаются.

So Node.js understands ESM modules, add one line to package.json: "type": "module". Without it Node treats .js as CommonJS, and imports will break.

8. Workflow: type-check vs build

9. Source maps — мост между .ts и .js

9. Source maps — the bridge between .ts and .js

Когда TypeScript компилируется в JavaScript, исходный код заметно меняется: исчезают типы, типы-литералы превращаются в обычные значения, иногда переписываются конструкции. Source map — это файл .js.map, который говорит отладчику: «строка 5 в .js = строка 12 в твоём .ts».

When TypeScript compiles to JavaScript, the source changes noticeably: types disappear, literal types turn into regular values, sometimes constructs are rewritten. A source map is a .js.map file telling the debugger: "line 5 in .js = line 12 in your .ts".

Опция "sourceMap": true создаёт такой файл. Это даёт три суперспособности:

The "sourceMap": true option creates this file. It grants three superpowers:

  1. Stack-трейсы ошибок ссылаются на ваш .ts-код, а не на скомпилированный .js.
  2. Брейкпоинты в VS Code работают прямо в .ts-файлах — даже если выполняется .js.
  3. DevTools браузера показывают ваш TypeScript, а не «прожаренный» JS.
  1. Error stack traces point at your .ts code, not the compiled .js.
  2. Breakpoints in VS Code work right in .ts files — even when .js is what's running.
  3. Browser DevTools show your TypeScript, not the "baked" JS.

10. Watch mode: the compiler as helper
